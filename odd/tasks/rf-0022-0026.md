# RF-0022, RF-0026 — Purchase order lifecycle and inventory valuation query

Objective: manage purchase orders through their approved lifecycle (edit drafts, cancel before receipt, replace a cancelled order) and let managers and administrators consult the weighted-average valuation of a branch (Spring Boot + PostgreSQL + React).
Branch: `feat/rf0022-rf0026` from `main` 4bc9718. Delivery: work-unit commits, no push. Runners: Maven Docker runner (`backend/README.md`), `pnpm test` / `pnpm build`.

## Specs

- **S1 (RF-0022, INC-011/D01, D03):** «borrador → pendiente de recepción → recibida; cancelación antes de recibir. Solo editar borradores. Pendiente no se reescribe: cancelar y crear otra conservando ambas. Recibida no se borra. Sin aprobación de compra, tesorería, pagos ni recepción parcial.» Actors: «operador gestiona órdenes de su sucursal; gerente supervisa propias y administrador consulta la red.»
- **S2 (RF-0022-CA-01):** «dada una orden, cuando el operador ejecute una transición válida del ciclo aprobado, entonces se reflejará su estado y relación con recepción, si aplica; intentar editar una pendiente o borrar una recibida se rechazará sin alterar sus datos ni inventario.»
- **S3 (RF-0022-CA-02, RF-0026-CA-01):** «dada una orden pendiente que necesita cambios, cuando se cancele y cree otra, entonces permanecerán consultables ambas con sus estados; cancelar antes de recibir no modificará stock ni promedio ponderado.» «Una compra cancelada no altera el resultado.»
- **S4 (RF-0026, user L2):** «consulta de valoración por gerente propio/administrador, no operador.» «promedio a 6 decimales, importes mostrados a 2 y mitad hacia arriba (§5.4).» RF-0026-CA-04: «cuando se consulte antes de corregir, entonces habrá saldo registrado de 8 unidades/valor 120/promedio 15.»
- **S5 (frontend):** purchases and valuation views integrated with the real API, following `docs/08-implementacion/sistema-visual.md`, with loading, success, empty, validation and error states.

Assumptions (technical, not functional): writes follow the existing convention `POST /purchases/orders/{id}/update` and `/cancel` with `Idempotency-Key`; the cancellation reason is optional (data model §6.3 `purchases_event.reason`: «Motivo si corresponde; no imponer dato funcional nuevo»); a replacement references a cancelled order of the same branch through `replaces_order_id`, and a cancelled order is replaced at most once; deletion of orders has no endpoint (the API answers 405); editing a draft replaces its lines, so the runtime role gets `DELETE` on `purchases_line` guarded by a trigger that only allows it for lines of draft orders; the valuation query is `GET /inventory/branches/{branch}/valuation`.
